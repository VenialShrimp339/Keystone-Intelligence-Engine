# Prompt versioning and drift control in OpenClaw and Claude Code

**Both OpenClaw and Claude Code converge on one principle: the prompt is a version-controlled artifact, not a field in a config UI — but they diverge sharply on everything else.** OpenClaw splits the agent's identity across seven Markdown files in a workspace directory, with a hardcoded priority map and character-level truncation caps. Claude Code assembles ~20 conditional sections at runtime around a single source-level `__SYSTEM_PROMPT_DYNAMIC_BOUNDARY__` marker that decides which content is globally cacheable. Neither system has a formal "tuned-for-model-X" annotation convention — both treat model drift as a git problem. Checkpoint/resume is where the architectures diverge most: Claude Code offers explicit `--resume`, `--continue`, and `/rewind` file-checkpoints; OpenClaw has no resume flag at all because sessions are addressable by routing key and resume happens implicitly when the next message arrives. The sections below ground every specific identifier in a primary source, flag low-confidence claims, and surface where Peter Steinberger and Boris Cherny have spoken publicly about these design choices.

Unless noted otherwise, identifiers are drawn from `docs.openclaw.ai`, `code.claude.com/docs`, the `openclaw/openclaw` and `anthropics/claude-code` GitHub repositories, and the Pi coding-agent docs (`badlogic/pi-mono`) that OpenClaw wraps.

## 1. OpenClaw's bootstrap hierarchy and truncation system

OpenClaw is a **gateway-based multi-channel agent** (Telegram/Signal/WhatsApp/Discord/Slack/Web/macOS) that wraps the `@mariozechner/pi-coding-agent` runtime, internally called "Pi." Every session injects a fixed set of Markdown files from the agent workspace (default `~/.openclaw/workspace/`) into a block the runtime labels **"Project Context"** at the top of the system prompt. The docs describe the bootstrap surface as *"OpenClaw-owned and does not use the pi-coding-agent default prompt"* (`docs.openclaw.ai/concepts/system-prompt`, high confidence).

**Each file owns exactly one concern.** `SOUL.md` carries persona, tone, and ethical boundaries — Steinberger's key architectural bet, inspired by Anthropic's Constitutional AI work. `AGENTS.md` is the operational manual: rules, routing, workflows, memory protocol. `IDENTITY.md` is a small (~5-line) identity card — name, emoji, role label — that loads early as an anchor against identity-replacement prompt injection. `USER.md` stores profile, preferences, and timezone for the human. `MEMORY.md` is the curated durable memory store, intentionally excluded from group chats to avoid leaking personal context. `TOOLS.md` holds environment-specific operational notes (SSH hosts, device IDs, aliases) — crucially, it **does not grant or revoke tool permissions**; configuration does that. `HEARTBEAT.md` is the checklist consulted on scheduled proactivity turns. Community templates also reference `BOOTSTRAP.md` (one-time onboarding interview) and `BOOT.md` (optional startup ritual), which sit in the same family but aren't in the required seven.

**Load order is hardcoded in the codebase as `CONTEXT_FILE_ORDER`, with lower numbers loading earlier** (GitHub issue `openclaw/openclaw#65438`, high confidence): AGENTS=10, SOUL=20, IDENTITY=30, USER=40, TOOLS=50, BOOTSTRAP=60, MEMORY=70. **HEARTBEAT.md is the sole member of `DYNAMIC_CONTEXT_FILE_BASENAMES`** and is placed *after* the prompt-cache boundary; everything else is part of the stable cacheable prefix. Sub-agent sessions receive only AGENTS.md and TOOLS.md — the rest is filtered out to keep spawned contexts small.

**The truncation system enforces two bounds** (`docs.openclaw.ai/concepts/context`, verified directly and cross-checked via VelvetShark's Memory Masterclass and `stack-junkie.com`): `agents.defaults.bootstrapMaxChars` defaults to **20,000 characters per file**, and `agents.defaults.bootstrapTotalMaxChars` defaults to **150,000 characters aggregate** — character counts, roughly 50K tokens. When a file exceeds the per-file cap, the runtime truncates silently and optionally injects a warning block controlled by `bootstrapPromptTruncationWarning` (values `off | once | always`, default `once`). When the aggregate would exceed the total, files are trimmed in reverse priority order; `/context list` and `/context detail` expose raw-vs-injected sizes and per-file `OK | TRUNCATED | MISSING` status. A well-documented failure mode (issue `#42084`) is that oversize MEMORY.md files get silently clipped and the agent mysteriously stops replying. A recent commit `aca216b` on the main branch references *"increase default bootstrapMaxChars from 20k to 40k chars"* — **medium confidence** the per-file default has moved to 40K at HEAD even though the published docs still cite 20K.

**Truncation is designed around prompt-cache economics.** OpenClaw splits the system prompt at `OPENCLAW_CACHE_BOUNDARY` into a stable prefix (tool definitions, skills metadata, most workspace files) and a volatile suffix (HEARTBEAT.md, inbound-metadata JSON, runtime timestamps). The dedicated "Current Date & Time" block deliberately contains only the timezone — no dynamic clock — so the prefix hash stays byte-identical across turns; agents call `session_status` when they need the live timestamp. `/status` reports cache-read ratios like *"📦 Cache: 99% hit · 15k cached, 69 new"* (issue `#25369`). **Compaction busts the prefix cache**, so the next turn pays a full cold-write — a direct cost penalty for over-aggressive summarization. The truncation caps themselves are cache-friendly in a perverse way: keeping MEMORY.md small and stable is not just a context-window concern but a dollars-per-turn concern, which is why VelvetShark and multiple community guides converge on "1,000–2,000 total words across all bootstrap files."

One detail that is often asserted and **not officially documented** is a 70/20/10 head/tail/marker truncation split cited by `laozhang.ai`; treat this as low-confidence. Another architectural caveat is that `bootstrap-extra-files` is not a supported config — issues `#39120` and `#51789` both request loading bootstrap files from subdirectories, and users currently work around it via the `agent:bootstrap` hook.

## 2. Claude Code's modular prompt and the dynamic boundary

Where OpenClaw persists its identity as files on disk, Claude Code **assembles its system prompt at session start from ~15 to 22 composable section functions**, selected by feature flags and a priority waterfall (override → coordinator → agent → custom → default). Post-leak reverse-engineering (Piebald-AI's per-release extractions, Drew Breunig's April 2026 interactive map at `dbreunig.com/2026/04/04/how-claude-code-builds-a-system-prompt.html`, Markdown Engineering Lesson 39, and the `ghboke/claude-code-reverse` DeepWiki) all converge on the same picture: an always-included core (identity line, system rules, Doing Tasks, Executing Actions With Care, Using Your Tools, Tone and Style, Output Efficiency) followed by a conditional tail whose membership depends on flags like `repl_mode`, `embedded_search`, `task_tool_enabled`, `COORDINATOR_MODE`, KAIROS proactive mode, and whether the user is an Anthropic employee.

**The cache-aware boundary is an explicit source-level constant**: `export const SYSTEM_PROMPT_DYNAMIC_BOUNDARY = '__SYSTEM_PROMPT_DYNAMIC_BOUNDARY__'` in `constants/prompts.ts`, with a source comment warning not to reorder sections without updating `splitSysPromptPrefix` in `utils/api.ts` and `buildSystemPromptBlocks` in `services/api/claude.ts` (community-reverse-engineered, high confidence). Content before the marker carries `scope: 'global'` in the API call and is cacheable across organizations on a **1-hour TTL**; content after it is per-session with the default **5-minute TTL** (`techtwitter.com/articles/the-breakdown-of-a-claude-code-prompt`; Claude Code Camp). A code comment in the leaked source reportedly states the design rule: *"Any runtime-conditional expression placed before the boundary multiplies the number of distinct cache-prefix hashes by 2 per condition"* — which is why engineers have explicitly migrated flags like non-interactive mode into a post-boundary `getSessionSpecificGuidanceSection`.

**CLAUDE.md is NOT injected into the system prompt parameter.** It is wrapped in a `<system-reminder>` XML block inside the *messages* array, prefaced with *"Codebase and user instructions are shown below ... These instructions OVERRIDE any default behavior"* (`claudecodecamp.com/p/inside-claude-code-s-system-prompt`, high confidence). This preserves the shared static prefix. The user-facing memory hierarchy loads **lowest-priority-first** (so higher-priority files land nearer the end, where the model attends more): managed (`/etc/claude-code/CLAUDE.md`) → user (`~/.claude/CLAUDE.md`) → project (walking upward from CWD) → local (`CLAUDE.local.md`, gitignored) → auto-memory (`~/.claude/projects/<slug>/memory/MEMORY.md`, first 200 lines or 25 KB). Project-root CLAUDE.md is **re-injected after `/compact`** but nested subdir CLAUDE.md files reload only the next time Claude reads a file in that directory. The registry distinguishes `systemPromptSection(name, compute)` (memoized until `/clear` or `/compact`) from `DANGEROUS_uncachedSystemPromptSection`, which currently has exactly one client — `mcp_instructions` — because MCP servers can connect or disconnect mid-session.

**On versioning: no standard "tuned-for-model" annotation exists.** The skill frontmatter schema supports a `version:` field, but the official docs describe it as *"primarily used for documentation and skill management purposes"* (`code.claude.com/docs/en/skills`, high confidence). The `model:` frontmatter field in skills and subagents selects the model at invocation, not the model the prompt was tuned for. Anthropic's internal convention is instead a source-code comment: every section in `prompts.ts` that needs review on each new model release carries a `// @[MODEL LAUNCH]` tag. Plugin distribution is the one place where a version field is enforced — `plugin.json` requires a mandatory `version` used by plugin install/update resolution. The **de-facto versioning pattern for CLAUDE.md is git itself**: commit it to the repo, evolve via PRs, let the git log be the version history. Awesome-claude-skills' guide puts it plainly: *"Version your skills — use git tags for version management."*

Model drift is handled at the edges, not in the prompt. The runtime's `env_info` section always injects the exact active model name and ID into the prompt each turn (e.g., *"You are powered by the model named Claude Opus 4.6. The exact model ID is claude-opus-4-6"*). The **auto-memory staleness-verification** subsection instructs the agent to delete memory entries that conflict with observed reality — but it compares memories against the codebase, not against model versions. A shipped skill called **"Model migration guide" (~18,052 tokens, per Piebald's Oct 2025 CHANGELOG)** walks humans through breaking changes, deprecated parameters, and prompt-behavior shifts when a new Claude model releases. Official release notes explicitly note things like *"Opus 4.7 performs well out of the box on existing Claude Opus 4.6 prompts"* — a deliberate cross-version compatibility signal.

A recurring operational trap: model aliases silently drift. `opus` resolves to Opus 4.7 on Anthropic's API but Opus 4.6 on Bedrock/Vertex/Foundry as of April 2026, so Anthropic recommends pinning via full IDs (`claude-opus-4-7`) or `ANTHROPIC_DEFAULT_OPUS_MODEL`. This is a real risk for prompts implicitly tuned against a specific model.

## 3. How OpenClaw's JSONL transcripts mark the compaction boundary

OpenClaw's transcripts live at `~/.openclaw/agents/<agentId>/sessions/<sessionId>.jsonl` alongside a `sessions.json` key-value index that tracks per-session metadata (current `sessionId`, token counters, `compactionCount`, `memoryFlushAt`, channel type, model override, `thinkingLevel`). The transcript schema is owned by Pi's `SessionManager`, not by OpenClaw itself, and is documented directly at `github.com/badlogic/pi-mono/blob/main/packages/coding-agent/docs/session.md`. Every line is a typed entry with `{type, id, parentId, timestamp}` — the tree structure via `id`/`parentId` supports branching conversations. The session header on the first line is `{"type": "session", "version": 3, "id": ..., "cwd": ..., "parentSession": ?}`; version 3 differs from v2 by renaming the `hookMessage` role to `custom`.

**The compaction boundary is not a flag or filter — it is a dedicated entry type**, and the key discovery here is that **no per-message `isCompacted`, `hidden`, or `preCompactionHidden` field exists anywhere in the schema**. Instead, a single `{"type": "compaction"}` entry is appended to the JSONL with the following structure (from `packages/coding-agent/docs/compaction.md`):

```json
{"type":"compaction","id":"f6g7h8i9","parentId":"e5f6g7h8","timestamp":"...",
 "summary":"User discussed X, Y, Z...","firstKeptEntryId":"c3d4e5f6",
 "tokensBefore":50000,"fromHook":true,"details":{"readFiles":[...],"modifiedFiles":[...]}}
```

**The `firstKeptEntryId` pointer is the authoritative boundary.** Entries whose tree position is before `firstKeptEntryId` are pre-compaction and omitted from the next model turn; entries at or after it are "kept." The compaction entry itself carries the `summary` string that replaces the omitted span. Issue `#30134` shows a real on-disk line with `tokensBefore=182599 fromHook=true`. The `fromHook` boolean distinguishes **extension-generated compactions** (e.g., OpenClaw's gateway hook) from Pi's built-in path. On repeated compactions, the summarized span starts at the *previous* compaction's kept boundary, not at the new compaction entry.

**The full pre-compaction history stays on disk — compaction never mutates earlier lines.** Quote: *"The full conversation history stays on disk. Compaction only changes what the model sees on the next turn"* (`docs.openclaw.ai/concepts/compaction`). Downstream tools therefore reconstruct the partition by parsing the JSONL, walking the parent-chain from the active leaf, finding compaction entries, and applying `firstKeptEntryId` — not by filtering on any message-level flag.

**Visibility controls exist but are scoped to navigation rather than filtering.** The `/tree` command navigates and views the entire pre-compaction history in place. Pi's TUI ships a Ctrl+O filter cycle with modes `default → no-tools → user-only → labeled-only → all`. OpenClaw's CLI exposes `openclaw sessions`, `sessions cleanup`, `sessions prune`, and `sessions archive`, but **none filter by compaction boundary** — the research found no `--include-pre-compaction` or `--hide-compacted` flag. The agent-facing `sessions_history` tool returns only the active session and does not expose archived/pre-reset transcripts; this is a known gap (`#57139`). Programmatic hooks exist on the Pi side: a `compaction_end` RPC event with `{reason: "manual"|"threshold"|"overflow", result, aborted, willRetry}` and `session_before_compact` / `session_compact` extension hooks.

**Tool-call/result pairing across the boundary is an explicit design guarantee** (`docs.openclaw.ai/concepts/compaction`): *"If the token-share split lands between a tool call and its result, OpenClaw shifts the boundary to the assistant tool-call message instead of separating the pair. If a trailing tool-result block would otherwise push the chunk over target, OpenClaw preserves that pending tool block and keeps the unsummarized tail intact."* File operations survive semantically via `details.readFiles` and `details.modifiedFiles` in the compaction entry, even when the raw tool output is summarized away. A separate mechanism, **session pruning** (`contextPruning.mode: "cache-ttl"`), trims old tool results from the in-memory context before each LLM call but **does not rewrite the JSONL** — the transcript is always more complete than the live model view. Compaction persists in the JSONL; pruning does not.

Note on source reliability: the task referenced DeepWiki sections "5.3 and 5.5" for session management, but current DeepWiki structure places OpenClaw session management under section 2.4. No content exists at the numbered sections requested — this appears to be stale pagination.

## 4. Checkpoint and resume semantics compared

The two harnesses make **fundamentally different assumptions about what a session is.** Claude Code treats a session as a linear, user-owned conversation artifact on a single machine; OpenClaw treats it as a routed conversation bucket keyed by `(agentId, channel, peer)`. This shapes every decision below.

**Claude Code offers explicit resume commands.** `claude --continue` (alias `-c`) resumes the most recent session in the current directory. `claude --resume [session-id|name]` (alias `-r`) accepts a UUID or human-readable name or opens an interactive picker; in the picker, `A` widens to all projects and `B` filters by git branch. `claude --continue --fork-session` branches without mutating the original. `claude --from-pr <num|url>` resumes a PR-linked session. In-session slash commands include `/resume`, `/rename`, `/rewind` (alias `/checkpoint`, also Esc+Esc), `/compact`, `/clear`, `/btw`. The Agent SDK exposes `continue: true`, `resume: sessionId`, `forkSession: true`, plus helpers `listSessions()`, `getSessionMessages()`, `renameSession()`, `tagSession()`.

**OpenClaw has no resume flag.** `openclaw sessions`, `sessions cleanup`, and `sessions archive` manage session data, but resume is **implicit via routing** — the next inbound message on a `sessionKey` lands in the existing session. `/new` or `/reset` allocates a new `sessionId` within the same `sessionKey` (the previous transcript is archived as `<sessionId>.jsonl.reset.<timestamp>`). A closed-not-planned feature request (`#10599`) asked for a webchat session browser.

**State persisted by Claude Code**, per each turn, into `~/.claude/projects/<encoded-cwd>/<session-uuid>.jsonl` (non-alphanumerics in CWD become `-`): every user/assistant message, full tool calls with inputs, **full tool results including bash output and file reads**, extended-thinking blocks, subagent spawn events and summaries, per-turn token usage and model, `cwd` and git snapshots, and session metadata with a `parentUuid` chain plus `isCompactSummary` flags. **File checkpoints** (the `/rewind` subsystem) live separately at `~/.claude/file-history/{sessionId}/<filehash>@v<n>` — Claude snapshots every file touched by Write/Edit/NotebookEdit before each edit (path from `blog.vincentqiao.com`, **medium confidence** because official docs only say "stored locally, separate from git"). A global `~/.claude/history.jsonl` indexes every prompt ever sent. Session-scoped permissions, in-memory TodoWrite state beyond what's embedded in messages, and terminal env vars are **not persisted**.

**State persisted by OpenClaw** spans two layers. `sessions.json` is a map `sessionKey → SessionEntry` holding `sessionId`, `updatedAt`, channel metadata, token counters (input/output/total/context), `compactionCount`, `memoryFlushAt`, `memoryFlushCompactionCount`, and toggles (`thinkingLevel`, `verboseLevel`, `providerOverride`, `modelOverride`, `authProfileOverride`, `sendPolicy`). The per-session JSONL transcript stores the entry tree described in §3. Adjacent stores include `memory/YYYY-MM-DD.md` (written by the pre-compaction flush), `~/.openclaw/cron/runs/<jobId>.jsonl` for scheduled jobs, and `*.reset.<timestamp>` archives with configurable `resetArchiveRetention` (default 30 days).

**Where OpenClaw loses data is documented and operationally significant.** Issue `#62442` (April 2026, open, severity High): *"Session state is not persisted/restored. Sub-agent sessions are not reattached. Conversation bindings are lost. Task execution halts until a human manually resumes the session."* Sub-agents spawned via `sessions_spawn` use UUID-based keys, and issue `#19780` confirms those are **dead on gateway restart** — there is no stable-name binding to resume them. ACP sessions spawned from hooks similarly lose binding (`#54342`). Cron runs start a fresh session ID each time by design. The gateway defers restart until pending operations complete, but any in-memory autonomous-task state is lost on restart. **Claude Code has its own tool-call corruption issue** (`#3003`): interrupting during tool calls can leave a `tool_use` block without a matching `tool_result`, and Anthropic's API rejects the next `--resume` with a mismatch error. On a single Esc graceful interrupt, Claude Code injects a synthetic "interrupted by user" tool_result; on double Ctrl+C or parallel-tool kills, the injection is unreliable.

**Cross-machine resume** is not native in either system. Claude Code requires copying the JSONL to the same encoded-CWD path on the target machine; Anthropic's own docs explicitly warn *"Don't rely on session resume [across hosts]. Capture the results you need as application state and pass them into a fresh session's prompt."* Third-party wrappers like Depot's `depot claude --resume <name>` watch the JSONL and sync via API. OpenClaw is architecturally gateway-centric — all state lives on the gateway host and clients (macOS app, WebChat, TUI, mobile) query it remotely over WebSocket, which is the intended multi-device pattern, though there is no built-in file sync.

**Explicit checkpoint primitives** differ dramatically. Claude Code has two: (1) **file checkpoints** via `/rewind` with four restore modes — code+conversation, conversation-only, code-only, "summarize from here" — but these do **not track** bash-invoked file mutations (`rm`, `mv`, `sed -i`), external edits, or remote side effects (DBs, APIs, deploys); (2) per-message UUID checkpoints exposed in the SDK as `rewindFiles(checkpoint_uuid)`. OpenClaw has **no `/rewind` analog** and no file-edit undo; it relies on git in the workspace. Its closest primitive is the **pre-compaction memory flush** (`agents.defaults.compaction.memoryFlush`, default enabled, `softThresholdTokens: 4000`) that runs a silent `NO_REPLY`-tagged turn before auto-compaction to write durable notes to `memory/YYYY-MM-DD.md`. Reset archives and `branch_summary` entries function as implicit rollback snapshots. Neither system has a true "save-and-pause" primitive for full agent state including in-flight tool calls.

| Dimension | Claude Code | OpenClaw |
|---|---|---|
| Resume entrypoint | `--resume`/`--continue`/`/resume` | Implicit via `sessionKey` routing |
| Storage root | `~/.claude/projects/<encoded-cwd>/` | `~/.openclaw/agents/<agentId>/sessions/` |
| File-edit undo | `/rewind` with 4 modes + separate file-history tree | None; relies on git |
| Compaction on disk | `isCompactSummary` flag + new session file on rollover | Inline `{type:"compaction"}` entry with `firstKeptEntryId` |
| Sub-agent durability across restart | Subagents return summaries; fresh context per invocation | **Dead on gateway restart** (`#19780`, `#62442`) |
| Permission state on resume | Lost (re-approve) | Toggles persisted in `sessions.json` |
| Retention default | 30 days (`cleanupPeriodDays`) | 30 days + `maxEntries: 500`, `rotateBytes: 10MB`, daily 4 AM reset |

## 5. What the founders actually say

**Peter Steinberger's design philosophy is unusually direct about not engineering prompts at all.** On the Lex Fridman podcast (#491, released Feb 12, 2026, full transcript at `lexfridman.com/peter-steinberger-transcript/`), he describes the origin of SOUL.md as reaction against Claude's default voice: *"When I built it in the beginning, my agent had no personality. It was just ... Claude Code. It's like this sycophantic opus, very friendly. And I ... When you talk to a friend on WhatsApp, they don't talk like Claude Code."* He then **had the agent write its own SOUL.md**, producing the now-famous line that ships as a de-facto template: *"If you are reading this in a future session, hello. I wrote this but I won't remember writing it. It's okay. The words are still mine."* He frames agent-building as context engineering, not prompt engineering: *"I used to write really long prompts ... I just use bespoke prompts to build my software."* On model drift, Steinberger avoids prescribing prompts against specific model versions — instead he contrasts **personalities**: Claude Opus as "too American, friendly, fast, trial-and-error, a little silly"; GPT-5.3 Codex as *"the weirdo in the corner that you don't want to talk to, but is reliable and gets shit done."* He prefers Codex because *"it reads more code by default and requires less charade."* On HEARTBEAT.md he is equally unromantic: "Isn't that just a cron job?" he says Lex asked him — *"yes, and isn't love just evolutionary biology?"*

**Steinberger's announcement post** (`steipete.me/posts/2026/openclaw`, Feb 2026) frames OpenClaw moving to a foundation as an openness commitment: *"It's always been important to me that OpenClaw stays open source ... It will stay a place for thinkers, hackers and people that want a way to own their data."* On the Hanselminutes podcast (episode #1036) he discusses the personal-agent workflow and iterative prompt tuning, though primarily anecdotally. The public record shows **no direct commentary from Steinberger about versioning prompts against specific model releases** — his design bet is that personality and context (SOUL.md + workspace files) transfer across models better than model-tuned prompts do.

**Boris Cherny's public commentary is denser and more prescriptive.** The core quote, repeated across his appearances: *"You should never have to correct Claude twice for the same mistake."* This drives his team's **"Compounding Engineering"** workflow — a single CLAUDE.md checked into git, updated by everyone on the team multiple times a week, with corrections added via PR comments like `@claude add to CLAUDE.md to never use enums, always prefer literal unions`. The Claude Code GitHub Action (`/install-github-action`) commits the update automatically. He is explicit about not over-documenting: *"I wouldn't try to kind of pre-add a bunch of stuff if you don't actually see Claude struggling with it"* (Pragmatic Engineer, March 2026 interview; also reiterated on `howborisusesclaudecode.com`).

On model drift, Cherny's stated position is to **build slightly ahead of the current model**: *"Don't design your workflows around the limitations of today's model. Build for where the technology will be in six months."* (Lenny's Newsletter, Feb 19, 2026). When Opus 4.7 shipped in April 2026, his published recommendation was to tune effort levels and add verification steps, **not** to retune CLAUDE.md. On verification as the core quality multiplier: *"Probably the most important thing to get great results out of Claude Code: give Claude a way to verify its work. If Claude has that feedback loop, it will 2-3x the quality of the final result."* On subagents as a temporary bridge: *"Sub-agents are a bridge for models of today"* — he expects them to dissolve as models get better at managing their own context.

On the earlier Latent Space podcast (May 2025, `latent.space/p/claude-code`), Cherny and Cat Wu discussed memory: they **considered vector stores and RAG for CLAUDE.md but deliberately chose file-based markdown** — *"Do the simple thing first ... the simplest implementation is often the best."* They cited the **Bitter Lesson**: eventually the model will manage memory on its own, so don't over-engineer it. Early prototypes used vector-store RAG; they switched to agentic search (grep, glob) because *"[it] performs a lot better based on benchmarks and vibes"* and avoids indexing complexity, staleness, and external dependencies.

**The contrasting philosophies are revealing.** Steinberger optimizes for *personality and user delight* across models — a prompt architecture explicitly designed to be portable and gradually co-authored by the agent itself. Cherny optimizes for *correction efficiency and team-scale institutional memory* — a prompt architecture where every mistake compounds into permanent, git-versioned team knowledge. Neither has published a formal model-drift procedure or a "tuned-for-X" annotation standard. Both rely on git as the version-control substrate and on human review as the drift-detection layer.

## Conclusion: what this means for building a multi-agent system

The architectural lesson is that **prompt versioning, drift detection, and checkpoint/resume are not three problems — they are one.** Both systems independently arrived at the same solution: make prompts files, version them in git, and let ordering rules (OpenClaw's priority map, Claude Code's dynamic boundary) decide what's cacheable versus volatile. Neither team built model-tuning annotations because **git blame plus release-note migration guides have proven good enough** — the runtime just injects the current model ID into the prompt (Claude Code's `env_info` section) and trusts the model to adapt. If you're building a multi-agent research harness, the strongest takeaways are: (a) separate stable identity from volatile context with an explicit cache boundary, (b) treat the transcript as an append-only structural artifact where compaction is a new entry type rather than a mutation of old ones, (c) preserve tool-call/result pairs across any summarization cut as a hard invariant, (d) design checkpoint primitives at two layers — message-level (implicit) and file-level (explicit) — and accept that in-flight tool calls are the hardest failure mode, and (e) resist the urge to annotate prompts for model versions; the drift-detection work happens at the edges (release-note reading, effort-level recalibration, verification agents), not in the prompt file itself. OpenClaw's open `#62442` and Claude Code's chronic `#3003` tool-corruption issue are the two warnings to carry forward: both harnesses struggle most precisely where autonomous work meets process restart, and that gap is where your architecture will earn its keep.
