# Long-term memory in agent systems, April 2026

**Executive summary.** Of the two products under review, **OpenClaw is a real, open-source agent framework** (Peter Steinberger / @steipete; `github.com/openclaw/openclaw`) and almost every named internal the user asked about — `memory-core`, `ContextEngine`, `QMD`, Light/REM/Deep dreaming, `prepareSubagentSpawn`, `onSubagentEnded`, `recencyHalfLifeDays`, `maxAgeDays`, and the v2026.3.7 and v2026.4.10 release tags — checks out against `docs.openclaw.ai` and signed GitHub release notes. The notable deviations from the user's framing are (a) dreaming phases run in the order **light → REM → deep**, not Light/Deep/REM, and only the Deep phase writes to `MEMORY.md`, and (b) the word "blocking" applied to the v2026.4.10 Active Memory sub-agent is not verbatim in the release notes, which describe a pre-reply sub-agent turn. For **Claude Code**, Anthropic's own documentation supports `CLAUDE.md` + `MEMORY.md` + per-topic files, a `/memory` command, and `/compact` as the real consolidation feature. The feature names **`autoDream`** and **`KAIROS`** do *not* appear in any official Anthropic documentation; they are community reconstructions from a March 31 2026 source-map leak of `@anthropic-ai/claude-code@2.1.88`. The literal phrase **"memory as hint, not truth"** is likewise not in Anthropic docs, though a weaker form ("context, not enforced configuration") is. The confidence table at the end classifies every claim.

## Part 1 — OpenClaw `memory-core`, dreaming, Active Memory, QMD, compaction flush, aging

**OpenClaw is a real, MIT-licensed agent framework** maintained by Peter Steinberger (@steipete) at `github.com/openclaw/openclaw`, with documentation on the Mintlify-hosted site `docs.openclaw.ai`. Its memory model is local-first and file-based: a durable `MEMORY.md` loaded at the start of every session, daily `memory/YYYY-MM-DD.md` notes (today and yesterday auto-loaded), and an optional `DREAMS.md` "dream diary." The workspace default is `~/.openclaw/workspace`. Memory is exposed to the agent through two tools, `memory_search` (semantic/hybrid) and `memory_get` (targeted read), over one of three backends — Builtin SQLite (default), **QMD** (local-first sidecar), or Honcho (plugin install).

**The `memory-core` plugin is real and is the default bundled memory slot.** It is selected via `plugins.slots.memory = "memory-core"` with configuration under `plugins.entries.memory-core.config`. Verified source paths (referenced across GitHub issues #66947 and #68995 and DeepWiki) include `extensions/memory-core/src/dreaming-markdown.ts` (exporting `writeDailyDreamingPhaseBlock`) and `extensions/memory-core/src/memory/qmd-manager.ts` (class `QmdMemoryManager`), plus its companion test `qmd-manager.slugified-paths.test.ts`. The per-agent SQLite index defaults to `~/.openclaw/memory/<agentId>.sqlite`. Specific line numbers were not recovered from the sources checked and are reported here only as file-level paths.

**Dreaming phases are Light → REM → Deep, not Light/Deep/REM.** Official documentation at `docs.openclaw.ai/concepts/dreaming` states verbatim, *"Each sweep runs phases in order: light -> REM -> deep."* The **Light** phase is ingestion/staging of short-term signals; **REM** *"extracts patterns and reflective signals"* and writes a managed `## REM Sleep` block to `DREAMS.md`; **Deep** *"decides what becomes long-term memory… appends promoted entries to MEMORY.md"* and writes a `## Deep Sleep` summary. **Only the Deep phase promotes entries into `MEMORY.md`** — several third-party write-ups (including at least one at `remoteopenclaw.com`) incorrectly describe REM as the write phase; those are source-quality noise, not product behavior. The default schedule is the cron expression `0 3 * * *` (daily at 03:00). Deep-phase thresholds documented at `docs.openclaw.ai/cli/memory` are `minScore=0.8, minRecallCount=3, minUniqueQueries=3, recencyHalfLifeDays=14, maxAgeDays=30`. The six weighted signals (Relevance 0.30, Frequency 0.24, Query diversity 0.15, Recency 0.15, Consolidation 0.10, Conceptual richness 0.06) are consistent across third-party sources but were not located verbatim on `docs.openclaw.ai`; treat those weights as corroborated-but-not-primary.

**The v2026.4.10 "Active Memory" sub-agent is real, but "blocking" is the user's word, not the release notes'.** The signed GitHub release `openclaw/openclaw/releases/tag/v2026.4.10` states verbatim: *"add a new optional Active Memory plugin that gives OpenClaw a dedicated memory sub-agent right before the main reply, so ongoing chats can automatically pull in relevant preferences, context, and past details without making users remember to manually say 'remember this' or 'search memory' first. Includes configurable message/recent/full context modes, live /verbose inspection, advanced prompt/thinking overrides for tuning, and opt-in transcript persistence for debugging."* The functional semantics are pre-reply, i.e. the sub-agent turn runs before the main reply — which implies synchronous blocking on that turn — but the specific string "blocking" was not found in the release notes or the referenced docs page (`docs.openclaw.ai/concepts/active-memory`, which was not directly retrieved). The system prompt template used by the Active Memory sub-agent was not recovered from the sources checked; release notes only reference "advanced prompt/thinking overrides for tuning."

**QMD is the real retrieval backend name; its expansion is contested across sources.** QMD is documented at `docs.openclaw.ai/concepts/memory-qmd` as an experimental local-first sidecar installed as the `@tobilu/qmd` npm package, enabled via `memory.backend = "qmd"`. Files live under `~/.openclaw/agents/<agentId>/qmd/` following XDG conventions. DeepWiki and the `QmdMemoryManager` source expand QMD as **"Queryable Markdown"**, while VelvetShark and josecasanova render it as **"Query Markdown Documents"** — **the official docs page simply uses "QMD Memory Engine" without spelling out the acronym.** All verified sources describe a **hybrid BM25 + vector + reranking** pipeline, but the precise score-combination rule (reciprocal rank fusion, weighted sum, or learned combiner) and the default `k` values at each stage **were not found in the sources checked and are not reported here**. Multiple GitHub issues (#8786, #9000, #9143, #9367, #9605, #9645, #9690, #9705, #10042, #10191, #10797, #11308, #65553) document active bugs, evidence of an under-active-development feature rather than a stable spec.

**Pre-compaction memory flush is documented and on by default.** The `docs.openclaw.ai/concepts/memory` page states verbatim: *"Before compaction summarizes your conversation, OpenClaw runs a silent turn that reminds the agent to save important context to memory files. This is on by default — you do not need to configure anything. The memory flush prevents context loss during compaction."* The configuration path is `agents.defaults.compaction.memoryFlush`, with sub-keys `enabled`, `softThresholdTokens`, `systemPrompt`, and `prompt`. **The default numeric value of `softThresholdTokens` was not located in the sources checked** — only the key name. GitHub issue #68995 indicates that flush writes are constrained to `memory/YYYY-MM-DD.md`, i.e. only the daily-note file, not arbitrary memory paths.

**Aging is controlled by `recencyHalfLifeDays` and `maxAgeDays`, introduced in v2026.4.5.** The release notes for v2026.4.5 state verbatim: *"Memory/dreaming: add configurable aging controls (recencyHalfLifeDays, maxAgeDays) plus optional verbose logging."* The CLI docs page `docs.openclaw.ai/cli/memory` shows the defaults as `recencyHalfLifeDays=14` and `maxAgeDays=30`, both in the Deep-phase promotion block. Issue #66078 confirms both values surface through `openclaw memory status --deep`. They are Deep-phase promotion thresholds (entries older than `maxAgeDays` are excluded from promotion candidates; recency score decays on a half-life of `recencyHalfLifeDays`), not retrieval-time filters on `memory_search`. Their interaction with eviction was not explicitly documented in the sources checked beyond the promotion logic.

## Part 2 — Claude Code: CLAUDE.md, MEMORY.md, `/compact`, and the leaked terms

**Claude Code documents two complementary memory systems, not three.** The canonical page at `code.claude.com/docs/en/memory` (mirrored to `docs.claude.com` and `docs.anthropic.com`) states verbatim: *"Claude Code has two complementary memory systems. Both are loaded at the start of every conversation."* These are (1) **CLAUDE.md files** — user-written persistent instructions — and (2) **Auto memory** — notes Claude writes itself, stored as `MEMORY.md` plus per-topic files. So `CLAUDE.md` and `MEMORY.md` both exist with distinct roles; they are not alternate names for the same thing.

**CLAUDE.md locations, verbatim from the docs table:** managed policy at `/Library/Application Support/ClaudeCode/CLAUDE.md` (macOS), `/etc/claude-code/CLAUDE.md` (Linux/WSL), `C:\Program Files\ClaudeCode\CLAUDE.md` (Windows); project `./CLAUDE.md` or `./.claude/CLAUDE.md`; user `~/.claude/CLAUDE.md`; local and gitignored `./CLAUDE.local.md`. `AGENTS.md` is explicitly **not** read but can be imported via `@AGENTS.md` from within `CLAUDE.md`.

**MEMORY.md plus per-topic topic files is the real auto-memory structure.** The docs say: *"Each project gets its own memory directory at `~/.claude/projects/<project>/memory/`. The `<project>` path is derived from the git repository, so all worktrees and subdirectories within the same repo share one auto memory directory."* Inside that directory: `MEMORY.md` (the index), then topic files like `debugging.md`, `api-conventions.md`, etc. Precise thresholds from the docs: **"The first 200 lines of MEMORY.md, or the first 25KB, whichever comes first, are loaded at the start of every conversation."** Topic files are **not** loaded at startup — *"Claude reads them on demand using its standard file tools when it needs the information."* Retrieval is therefore filename-driven, not embedded or semantically indexed.

**The "three-layer design with grep-only transcript access" is a community synthesis, only partly supported by Anthropic docs.** Anthropic documents the first two layers clearly (MEMORY.md index + topic files). Transcripts exist — *"Each message, tool use, and result is written to a plaintext JSONL file under `~/.claude/projects/`, which enables rewinding, resuming, and forking sessions"* — but the docs do **not** frame transcripts as a memory retrieval layer. *"Sessions are independent. Each new session starts with a fresh context window, without the conversation history from previous sessions."* Grep-based transcript access during consolidation is described only in community analyses of the March 31 2026 source-map leak, not in Anthropic documentation.

**`autoDream` is not a shipped, documented Anthropic feature.** Searches of `docs.claude.com`, `code.claude.com`, and `anthropic.com/engineering` return zero hits for "autoDream," "Auto Dream," or "/dream." The name appears exclusively in reverse-engineering reports (claudefa.st, dev.to, VentureBeat, The New Stack, XDA Developers, implicator.ai, The Batch) of a leaked `.map` source file packaged in `@anthropic-ai/claude-code@2.1.88` on March 31 2026. Those analyses describe `services/autoDream/` as a background consolidation subagent gated behind a feature flag codenamed `tengu_onyx_plover`, with a trigger condition near "24+ hours since last run plus 5+ sessions," but Anthropic's only public statement on the leak was that it was *"a release packaging issue caused by human error, not a security breach"* — Anthropic has not confirmed any `autoDream` behavior. **The actual documented consolidation feature is `/compact`.** From `code.claude.com/docs/en/how-claude-code-works`: *"Claude Code manages context automatically as you approach the limit. It clears older tool outputs first, then summarizes the conversation if needed… To control what's preserved during compaction, add a 'Compact Instructions' section to CLAUDE.md or run `/compact` with a focus."*

**`KAIROS` likewise does not appear in any official Anthropic documentation.** It surfaces only in post-leak reporting as a compile-time-gated daemon-mode feature flag (roughly 150 references in the leaked TypeScript), variously described as an always-on background mode with append-only daily logs and a ~15-second blocking budget. It is not a feature flag exposed to users, not an experimental-access program, and not an eval harness per any primary source I could reach. Treating KAIROS as a documented Claude Code feature would be inaccurate; it is community reverse-engineering of unshipped code.

**The phrase "memory as hint, not truth" is not in Anthropic's published documentation.** The closest official statement, from `code.claude.com/docs/en/memory`, is: *"Claude Code has two complementary memory systems… Claude treats them as context, not enforced configuration. The more specific and concise your instructions, the more consistently Claude follows them."* And on enforcement: *"CLAUDE.md content is delivered as a user message after the system prompt, not as part of the system prompt itself. Claude reads it and tries to follow it, but there's no guarantee of strict compliance."* Community analyses of the leaked source quote a `memoryFreshnessText()` function that stamps stored memories with warnings like *"Memories are point-in-time observations, not live state"* — consistent with a "hint-not-truth" design, but again, that comes from the leak, not Anthropic's published docs.

**The `/memory` slash command is documented.** Verbatim: *"The `/memory` command lists all CLAUDE.md, CLAUDE.local.md, and rules files loaded in your current session, lets you toggle auto memory on or off, and provides a link to open the auto memory folder."* When the user asks Claude to "remember" something, the instruction is saved to auto memory by default; adding to `CLAUDE.md` requires asking explicitly.

## Part 3 — OpenClaw `ContextEngine` plugin interface (v2026.3.7)

**`ContextEngine` is real, shipped in v2026.3.7 via PR #22201 by @jalehman.** The release notes at `openclaw/openclaw/releases/tag/v2026.3.7` state verbatim: *"Agents/context engine plugin interface: add ContextEngine plugin slot with full lifecycle hooks (bootstrap, ingest, assemble, compact, afterTurn, prepareSubagentSpawn, onSubagentEnded), slot-based registry with config-driven resolution, LegacyContextEngine wrapper preserving existing compaction behavior, scoped subagent runtime for plugin runtimes via AsyncLocalStorage, and sessions.get gateway method."* The plugin slot is configured at `plugins.slots.contextEngine`; the default value is `"legacy"` (wrapping existing compaction behavior for backward compatibility). Documented third-party engines include `lossless-claw` (Martian Engineering) and `openviking`.

**The full set of seven lifecycle hooks** is therefore `bootstrap`, `ingest`, `assemble`, `compact`, `afterTurn`, `prepareSubagentSpawn`, and `onSubagentEnded`. Beyond the hook names, **precise TypeScript signatures, parameter types, and return-type contracts for `prepareSubagentSpawn` and `onSubagentEnded` were not retrieved from `docs.openclaw.ai/concepts/context-engine` or the release notes in the sources I checked.** Based on the names and the release-note phrasing ("scoped subagent runtime for plugin runtimes via AsyncLocalStorage"), `prepareSubagentSpawn` appears to be invoked prior to a sub-agent forking so the engine can curate the context payload handed to it, and `onSubagentEnded` is called on completion so the engine can decide what to persist, summarize, or discard from the returned transcript — but those behaviors are **inferred from naming and PR description, not quoted directly from an API reference.** Anyone relying on exact signatures should open the `context-engine` package source or the PR diff (#22201) rather than trust this paragraph.

**There are no additional hooks beyond those seven in the release notes.** The set is symmetric around the turn (no `beforeTurn`; only `afterTurn`) and asymmetric around tool calls (no `beforeToolCall` / `afterToolCall` hooks in the published interface). The `compact` hook is the only compaction-side extensibility point; the earlier-described pre-compaction memory flush (`agents.defaults.compaction.memoryFlush`) is a separate, always-on behavior of the default compaction path, not a hook exposed on the `ContextEngine` interface.

## Confidence and gaps

**Well-sourced (primary docs or signed release notes, quoted verbatim):** OpenClaw's existence and publisher; `memory-core` as the default memory plugin and its config shape; the dreaming phase order light → REM → deep; only the Deep phase writing to `MEMORY.md`; the default dreaming cron `0 3 * * *`; Deep-phase thresholds `minScore=0.8, minRecallCount=3, minUniqueQueries=3, recencyHalfLifeDays=14, maxAgeDays=30`; existence of the v2026.4.10 Active Memory plugin and v2026.4.5 aging-controls release; pre-compaction memory flush documentation and the `agents.defaults.compaction.memoryFlush` config path; existence of QMD as a hybrid BM25+vector+rerank local-first backend at `memory.backend = "qmd"`; v2026.3.7 `ContextEngine` plugin slot and the full list of seven hooks (`bootstrap, ingest, assemble, compact, afterTurn, prepareSubagentSpawn, onSubagentEnded`); default `plugins.slots.contextEngine = "legacy"`; Claude Code's two-system memory model, the 200-line / 25KB `MEMORY.md` cap, the `~/.claude/projects/<project>/memory/` layout, the `/memory` command behavior, and JSONL transcripts used for resume/rewind/fork.

**Partially sourced (corroborated across multiple secondary sources but not located verbatim on primary docs):** the six weighted dreaming signals and their exact weights (0.30/0.24/0.15/0.15/0.10/0.06); the claim that Active Memory runs "blocking" (the release notes say "right before the main reply," which implies synchronous behavior but does not use the word); the "three-layer with grep-only transcripts" framing of Claude Code memory (the first two layers are documented; grep-based transcript access during consolidation comes from leaked-source analyses); the "memory as hint, not truth" principle (the closest official wording is "context, not enforced configuration").

**Not verified in any primary source checked, reported here as unknown rather than estimated:** exact line numbers for any referenced `extensions/memory-core/*` file; the precise expansion of "QMD" (sources split between "Queryable Markdown" and "Query Markdown Documents"; the official title is just "QMD Memory Engine"); the QMD score-combination rule (RRF vs weighted sum vs learned) and the default per-stage `k` values; the default numeric value of `compaction.memoryFlush.softThresholdTokens`; the exact TypeScript signatures and return contracts for `prepareSubagentSpawn` and `onSubagentEnded`; the system/prompt template used by the Active Memory sub-agent.

**Not found, reported as nonexistent in official sources:** a literal Anthropic-documented **`autoDream`** feature (exists only in the March 31 2026 source-map leak of `@anthropic-ai/claude-code@2.1.88`; the real documented consolidation feature is `/compact` and auto-compaction); a literal Anthropic-documented **`KAIROS`** gate (exists only as a leaked compile-time feature flag, never shipped or announced); the literal phrase **"memory as hint, not truth"** in Anthropic docs (closest official wording is "context, not enforced configuration"). A conflation to flag: **KAIROS and autoDream are Claude Code concepts from the leak, not OpenClaw features** — any source that attributes them to OpenClaw is incorrect. OpenClaw's own consolidation system is "Dreaming" (Light/REM/Deep), which is distinct.

**Correction to the user's framing:** the dreaming phase ordering in the brief ("Light / Deep / REM") is out of order relative to the official docs, which specify light → REM → deep with only the Deep phase promoting entries to `MEMORY.md`. And of the five features the user warned might be speculative or misremembered, three are in fact real, primary-sourced OpenClaw features (`memory-core`, `ContextEngine` v2026.3.7, Active Memory v2026.4.10 with `recencyHalfLifeDays`/`maxAgeDays` aging), while two (`autoDream`, `KAIROS`) are genuinely not in any official Anthropic source and exist only as artifacts of a source-map leak.
